# POKEBOOK-01 readiness after HERMES-01 acceptance

Ready for separate scoping/authorization; no PokeBook UI implementation was started in closeout. Next-phase order is HERMES-01 accepted → POKEBOOK-01 → STRATEGY-01 → SYSTEM1-01A preparation/installation → SYSTEM1-01B battle control. PREP-01 envelope schemas/feasibility/candidates must become executable before strategy consumes them for real preparation decisions.

Existing persisted services: stable SOCIAL post IDs/author/claim/body/template records; bounded follower graph; deterministic `tick` feed distribution; actor-bound `feed_metadata`, `read_post`, `relationships` and explicit `expose` with atomic MEMORY receipts. The trusted host issues grants; the model/player UI must never receive stores or factories. Current `feed_metadata` returns only postID, author, seen and channel. `read_post` returns postID, author, published claims, body, visibility and templateVersion only after authorized exposure (or for the author). Public exposure attribution is viewer-safe; author-private evidence IDs/director episodes/operator logs are not feed fields. Existing trainer packets distinguish direct observations/reported claims/private owned episodes and remain strategy-free.

Known implementation gaps for POKEBOOK-01: player-specific authorized viewer projection (current `for_social_actor` validates trainer registry actors), menu entry/navigation/pagination/profile content, bounded localization/encoding and durable read-position/branch semantics. Do not expose the admin `social_state` or `director_memory` dump to the player to shortcut viewer permissions. Current Janice/Rick/Doug slices are authored test content, not a campaign-scale social graph. NPC event-driven exposure policy must be scoped explicitly and remain independent of player feed opening; existing controlled tick/expose services prove the distinction, not an implemented autonomous scheduler.

Native BRIDGE-03 currently provides only safe field notice and fixed YES/NO choice primitives: at most48encodedbytes/two24-character lines, ASCII allowlist, no silent truncation or pagination, one owned modal and BUSY during battle/Start/save/quest-log/script/transition locks. These are not a full feed/menu widget. POKEBOOK-01 must design and validate its native screen path within actual ROM headroom (224 EWRAM bytes remain) and preserve original story/menu/save functions. No LLM request belongs in a UI rendering/input wait. Store/bridge absence needs labeled bounded behavior, not fabricated history.

HERMES closeout supplies actual live model-sourced persisted post+episode, save/reload and fresh-memory recall evidence, with strict recipient disclosure. Strategy/preparation schemas, resource accounting, roster installation and full battle legal-action coverage remain future gates; they do not block authorized history display. Existing unmanaged savestate/hot-load/reset/rewind and cross-process power-loss limits remain. Broader profile/notification/challenge features need scope, not automatic inheritance from this readiness note.
