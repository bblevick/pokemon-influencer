# PREP-01: executable host preparation

PREP-01 implements feasibility and durable eligibility. It does not select, commit, consume or install a trainer team, call a model, or change the accepted FireRed ROM. Native Boulder acceptance status and final checks are recorded in `evidence/phase3/prep01/completion.json`; an absent or pending result is not acceptance.

The production adapter is `prep.store.PrepStore`; it extends the accepted Puppeteer/Social/Memory/World store. `prep.domain` consumes the accepted `OpeningContent` and pinned ROSTER catalog. `config/preparation_generation.json` v1 bounds enumeration at16 complete candidates,48 individual paths per growth step,256 examined packages,256KiB per envelope and32KiB per candidate. Catalog/content hashes remain unchanged. No opponent, player-party, post, briefing, matchup score or wall-clock age enters generation.

## Trusted native stage

The trusted stage is a **known WORLD-paired normal battery**, not a badge guess or a new bridge event. `prep.progression.read_boulder` verifies the accepted ROM/ELF, ELF-derived native save section lengths, pinned source-file hashes and checksum-valid latest slot. Sections1–4 reconstruct SaveBlock1. A matching agbcc probe yields flags offset0xEE0,288 bytes and SaveBlock1 size15720. `GetFlagAddr`/`FlagSet` use native flag-number byte/bit indexing. Only `FLAG_DEFEATED_BROCK=0x4B0` and `FLAG_BADGE01_GET=0x820` are read. Both must agree. `PewterCity_Gym_EventScript_DefeatedBrock` is the inspected source witness.

The normal-save intent, exact lifecycle receipt, drained event ACK barrier, counter increment, stable reads/fsync and unchanged canonical cursor remain mandatory. Only after those checks does one SQLite transaction append the native progression receipt, grant justified opportunities and publish the PREP checkpoint cutoff/hash together with the existing WORLD/MEMORY/SOCIAL/Puppeteer checkpoints. No NPC learns either flag through this adapter. Native truth and actor-scoped social evidence remain distinct.

The first experimental probe used GNU's default EABI and incorrectly reported15528 bytes. The native pairing was refused. Pinned agbcc and GNU APCS both report15720, equal to the actual ROM serialization. Same-launch recovery paired the already-written battery with its surviving intent/callback. This failure and recovery remain in evidence; neither a synthetic flag nor a second guessed save repaired it.

Supported scope remains fresh-process Continue and normal battery saves. Unknown batteries, unmanaged resets/hot loads/savestates/rewind, torn saves, gaps and unsupported builds fail closed. Eligibility updates at a validated normal-save checkpoint; it is deliberately not an immediate per-frame flag poll.

Querying does not initialize or reset anything. Evolution plans preserve that same lineage and origin. Resource initialization records the source trainer/content hash, actual stock, seven explicit zero categories and no restock. The opening actors receive no invented item, capture, teaching or evolution supply.

Rick/Doug's logical first post-Boulder opportunity ID depends on campaign/actor/stage. An abstract exclusive reservation records request ID/costs without selecting any candidate or debiting stock. Identical retries are idempotent; conflicting retries or finite deficits fail. Those writers remain deferred.

The last commitment/consumption transitions are a **pure downstream contract**, tested without a live commitment. CONTENT's already-consumed guard is tested with a labeled trusted-state fixture. No actual committed/consumed trainer plan is claimed. Rewind removes future receipts from the active prefix and increments the restore epoch; immutable abandoned history remains inspectable. Old envelopes/candidates cannot regain validity merely by restoring a later save.

## Complete packages and bounded diversity

`resolve_preparation_envelope(store, actor, stage)` returns a frozen host capability or a specific blocked result. Schema1 binds campaign, branch, actor, opportunity, restore epoch, canonical/PREP/MEMORY/SOCIAL/director cutoffs, activation, ROM/source/catalog/content/adaptation/generator/validator identities, own companions/resources, stage levels, aggregate budget, retention/signature/theme, native receipt and checkpoint evidence. Missing trusted ownership, inventory, stage or opportunity never produces an optimistic envelope.

`generate_preparation_candidates(envelope)` is pure. Every package contains exact lineage/species/level/four moves/held items/fixed-IV provenance, party order, native battle-item slots, complete sequential development paths and exact resource costs. The unchanged source-preserving package is offered as a fallback **option**, not selected. First-encounter packages also preserve the authored party order; alternative lead order is offered only for earned preparation opportunities. Configured structural enumeration gives each companion growth opportunities before bounded Cartesian combinations; growth/learning/evolution families rotate deterministically. Equivalent final packages are deduplicated. Examination/path/candidate bounds and omitted/rejected reasons are returned. No random draw or strength ranking occurs.

The validator reuses `OpeningContent.development` and source-backed ROSTER history queries, then checks the complete package, order, retained/signature lineages, all levels/moves/items/resources and Gym bounds. ROSTER's partial `fully_legal=false` element proofs are not relabeled. PREP's complete-package result explicitly means **a legal host plan for the qualified opening rules**, not a native installed team. Supplied descriptors/proof metadata are recomputed and checked; malformed, altered, wrong-generation or stale packets fail. Validation must be repeated with the active store before a later commitment.

Accepted CONTENT accounting remains conservative: every elective new learned slot, including intermediate/evolution learning, counts across the entire team; there are no free four-latest-move rewrites. Growth/evolution without learning does not consume an elective edit. Skipping an offered move is legal. Rick's target10 cannot grant Butterfree Stun Spore14, Sleep Powder15 or Gust28. Doug's original Kakuna may legally develop into Beedrill and learn its exact level-up move subject to the same aggregate2 budget.

`resolve_preparation_bundle` and `tools/prep01_report.py` return the envelope plus separately hashed candidate set. Their hashes are separate to avoid circular candidate→envelope→candidate identities. `selectedCandidateID` and commitment remain null; installed=false. Neutral descriptors include exact type composition/move types, evolved-companion count, elective edit count and non-damaging move count, with no opponent-conditioned score.
