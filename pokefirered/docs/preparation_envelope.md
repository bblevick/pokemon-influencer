## Authority and flow

A trusted preparation service builds `PreparationEnvelope` from pinned game rules, actor-owned companions/inventory, earned stage/epochs and authored identity/resource policies. It never takes hidden player party/moves/stats as input. Hermes supplies a separately authorized `NPCBriefing`; it cannot widen the envelope. Strategy interprets these inputs and emits subjective `StrategyMemo`. System One selects among complete validated candidates, not arbitrary edits. The deterministic commit service revalidates feasibility and spends/reserves resources atomically before locking a `PreparationCommitment`.

Generate a bounded diverse feasible candidate set/envelope before strategy. Pass neutral aggregate capabilities to Strategy; future System One receives the complete validated candidates and exact subjective memo. Additional intent-conditioned generation is optional future work; it must not require parsing prose into facts or permissions. Intent cannot increase limits or bypass acquisition rules. Record deterministic generation seed/version, excluded alternatives and rejection reasons. Avoid constructing an unbounded Cartesian product.

## PreparationEnvelope fields

All objects are closed, versioned host-domain packets. IDs are opaque references, not permissions. Host-issued grant binds actor, campaign, branch, restore/activation generations and cutoffs before serialization. Numeric budgets and packet/candidate bounds must come from reviewed versioned content/policy; no model invents them.

| Field | Required meaning |
| --- | --- |
| `schemaVersion`, `envelopeID`, `envelopeSHA256` | Contract version 1; immutable identity/hash of normalized envelope contents |
| `scope` | Campaign/branch/actor/opportunity/encounter IDs, first-encounter or rematch kind, restore/activation epochs, canonical/memory/social/puppeteer cutoffs |
| `rules` | ROM/source/catalog hashes, policy/content versions and generator version/seed; selected FireRed version only |
| `progression` | Earned named story/milestone predicates, eligible training epoch IDs, applied epochs, stage level targets/caps and per-epoch growth limits; no wall-clock age or loss-count growth |
| `companions` | Actor-owned persistent lineage IDs, current species/level/moves/acquisition provenance and fixed identity stats; active/reserve limits, signature IDs and required original-lineage floor |
| `inventory` | Finite owned quantities, existing reservations/spends, authorized acquisition grants; held-item allocation and consumable use distinguished |
| `acquisitionOptions` | Validated native/nearby map/method/access/resource references; evolution conditions; separately granted exceptional sources only; capture attempts/results come from game rules, never selector success |
| `moveOptions` | Per-lineage legal moves with acquisition method/level/epoch/cost/provenance: known, level-up, permitted TM/tutor or authored route; learnset presence alone does not authorize acquisition |
| `budgets` | Allowed move-slot changes, growth, captures/replacements, active/reserve changes and resource spend; already-applied effects cannot be repeated |
| `identityPolicy` | Archetype/signature/theme constraints, Gym primary theme, explicit mixed-type support allowance and first-encounter adaptation profile; missing profile retains authored baseline |
| `candidates` | Bounded complete validated preparation snapshots, stable candidate IDs/hashes, lineage→species/levels/moves/items/order, resource deltas/reservations, legality proof references and tactical descriptors |
| `generation` | Candidate count/byte limits, enumeration/truncation/coverage details, diversity categories and excluded-option reasons; explicitly expose when only baseline is feasible |
| `fallbackCandidateID`, `expiresAtEvent` | Validated unchanged/authored baseline; game-event invalidation boundary, not permission for wall-clock trainer growth |

The envelope describes own inventory/companions and legal possibilities; it is not a dump of the canonical world ledger. NPC knowledge is supplied separately with provenance. Provider serialization may omit correlation internals but must retain the host's exact stored input/hash and scope.

## Adjacent packets

`NPCBriefing` v1: host-bound actor/scope/cutoffs, authored personality, direct observations, attributed exposed claims, actor-permitted notes, provenance references, explicit unknowns/truncation and source versions. Director memory may guide which lawful notes are prepared, but each factual note needs an actor-authorized observation/delivery chain. Delivering a new claim requires a recorded targeted service receipt before it becomes knowledge. A director inference is a labeled hypothesis, never a canonical fact or direct observation. Current HERMES-01 trainer packets are a substrate; no general briefing delivery service is claimed implemented.

`StrategyMemo` schema3/prompt2: exact bounded subjective text with host-generated actor/scope/context/cutoffs/envelope/persona/provider/model/time provenance. No required model enums, numeric scores or evidence-ID extraction. System One receives the exact persisted memo separately from AUTHORIZED FACTS and complete legal candidates. The memo cannot widen feasibility or create knowledge. Historical StrategicPosture contracts remain replayable, not required new model output.

`PreparationSelectionRequest/Result` target v1: request identity, envelope/candidate-set hashes, exact memo reference/text in SUBJECTIVE section, authorized briefing/own state in FACTS section and supplied candidate IDs → exactly one candidate ID plus normalized provider/fallback diagnostics. IDs and optional scores must belong to the supplied current set. No species/move/item mutation payload is accepted. Provider capability to select these candidates must be separately verified; Mercury battle-choice support is not preparation support evidence. Deterministic offline selection uses the same interface.

`PreparationCommitment` target v1: stable commitment/opportunity/actor/branch IDs, selected candidate/envelope/exact-memo/briefing hashes, complete prepared snapshot, resource transaction/reservation IDs, generation/selection seed and versions, actual decision/fallback, evidence cutoffs and lock state. ROM installation acknowledgement and installed party hash bind an actual encounter to this snapshot.

## Validation, resource rules and lock

Validate schema/bounds → actor/scope/current opportunity → evidence permissions → catalog/source versions → candidate membership/hash → every species/level/evolution/move/item/acquisition/identity rule → available quantities/reservations → idempotent commit and lock. Revalidate before safe ROM installation; reject stale candidate sets/branches and invalid installations. Record every accepted or rejected decision. Model prose never executes constructors or game scripts.

Resource spending occurs once through explicit game-domain transactions. A reserved item is not a duplicated item; selected alternatives spend nothing. Retry reuses the same commitment/transaction. Held-item persistence, consumable deductions, capture outcomes, training grants and encounter healing/PP reset follow separately audited game rules. Battle consumption updates actual inventory; it does not authorize silently regenerating the locked preparation. Any allowed reset/replenishment must be an explicit rule, not a new model request. Preserve native healing behavior until an approved replacement is tested.

Lock before encounter readiness/installation. Later posts, briefing updates, player party changes, menu/feed opening, losses and retries cannot rebuild that encounter. New evidence is available only to a later eligible opportunity. Epoch opportunities are earned, applied once and saved with branches; always-on processing never creates growth from elapsed time. Restore excludes future commitments, notes, reservations and spends; replay uses stored accepted selections without new inference.

## Meaningful choice and acceptance gates

Where feasibility permits, offer materially distinct legal alternatives (moveset roles, held-item/consumable allocation, order/support or conserving resources), not several renamed copies of a preselected roster. Preserve an unchanged candidate. Report diversity/coverage and why alternatives are unavailable; never weaken constraints to satisfy a count. Intent-conditioned ranking must leave lawful alternatives for System One selection. Tests must demonstrate different intents can select meaningfully different feasible preparations on the same authorized state, and hidden-player swaps cannot change envelope/briefing/candidates.

For opted-in first Gym encounters, use stage-based existing companions and a finite authored starting resource envelope; do not fabricate earned rematch epochs or automatic catches. Keep signature companions and primary theme; bounded mixed-type support requires explicit content limits (slot count, level/stage, acquisition and change budget). Those numeric limits are outstanding content decisions, not an unlimited mixed-team authorization. Unconfigured ordinary/boss trainers retain authored first rosters. This is the explicit architectural expansion of PLAN's earlier authored-first-roster rule, not an implemented team change.
